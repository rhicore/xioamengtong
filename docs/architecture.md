# 系统架构和迁移边界

当前项目已经统一使用网页端。顾客端和运维端都调用同一个通用 HTTP API，CloudBase 只由服务端访问。这样可以避免前端暴露服务端密钥，也方便将来把后端存储迁移到自有服务器。

## 目录职责

```text
customer_web/
  顾客输入订单号、选择图片类型、裁切和上传图片

admin_web/
  员工登录、订单筛选、图片预览、批量下载和账号管理

backend_api/
  顾客接口、员工认证、订单业务、CloudBase 数据库/云存储适配和 ZIP 下载

docs/
  业务流程、平台识别、认证和部署说明

tests/
  不依赖线上账号的接口和前端构建测试
```

## 请求链路

```text
customer_web ─┐
              ├─> backend_api ─> CloudBase Database / Storage
admin_web ────┘
```

前端只负责展示和收集输入。订单查询、订单创建/更新、图片上传、临时图片 URL、后台权限和压缩包生成全部在 `backend_api` 内完成。

## 顾客流程

1. 顾客输入订单号。
2. `GET /api/v1/customer/orders/:orderId` 查询已有提交或返回可新建状态，并根据订单号启发式识别平台。
3. 顾客选择“两图”或“一张图”。
4. 顾客点击图片，在编辑器中更换、拖动和裁切图片。
5. `POST /api/v1/customer/orders/:orderId` 以 multipart/form-data 保存订单和图片。
6. 后端将原图裁切结果上传到 CloudBase 云存储，只把 fileID 写入 `orders` 集合。
7. 顾客再次输入同一订单号时，后端生成临时 URL，页面显示上次上传的图片并允许修改。

订单号不需要提前导入，首次提交会创建订单；再次提交会更新同一订单。当前不与淘宝、拼多多等外部平台通信。

## 后台流程

1. `POST /api/v1/admin/login` 校验员工账号和密码，服务端保存 bcrypt 密码哈希，并通过 HttpOnly Cookie 保存会话。
2. 订单列表、图片预览、批量下载和账号管理接口均由服务端检查会话和角色。
3. 批量下载按订单生成目录，目录中包含 `订单信息.json`、`前.jpg` 和 `后.jpg`（实际存在的图片才会写入）。

顾客接口和后台接口使用不同路由；顾客不需要员工账号，也不会获得数据库或云存储管理权限。

## 存储边界

`backend_api/src/cloudbase-store.js` 是当前 CloudBase 实现边界。业务模块只通过 store 接口读写数据和文件，不直接依赖 CloudBase SDK。以后迁移到普通服务器时，可以替换这个 store 实现，同时保留前端 HTTP 契约和页面代码。

订单保留历史兼容字段（例如旧本册代号和旧来源值），用于读取已有数据；新网页展示和提交只使用“两图”“一张图”等用户可理解的名称。

## 数据集合

- `orders`：订单号、本子类型、平台、图片 fileID、状态和时间字段
- `notebook_templates`：可选的动态本册类型配置；没有数据时使用后端内置默认值
- `staff_accounts`：员工账号、bcrypt 密码哈希、角色和禁用状态
- `staff_sessions`：哈希后的会话令牌和过期时间

## 将来扩展

- 增加网页顾客入口：直接复用 customer API，不复制数据库代码。
- 迁移存储：替换 store 的数据库和文件实现，不改变页面层。
- 大批量 ZIP：把同步生成改成任务队列/异步下载，不改变订单列表协议。
- 本册配置后台化：将模板读写从内置默认值切换为 `notebook_templates` 集合。
